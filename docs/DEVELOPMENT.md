# 개발 기록과 학습 가이드

이 문서는 구현의 이유를 설명하는 학습 자료입니다. 실제 작업 날짜나 작성자를 소급해 꾸미지 않습니다. 코드·테스트·AI 도구 제안을 직접 읽고 이해한 범위만 포트폴리오나 면접에서 설명하세요.

## 기능별 작업 단위

| 브랜치 | 작업 범위 |
|---|---|
| `feat/data-generator` | 재현 가능한 데이터 생성, SQLite 기반, 패키지 목록 |
| `feat/threshold-detector` | 표본 통계, 판정 이유, 경계값 테스트, 중복 방지 |
| `feat/dashboard` | 대시보드, 설비 상세, 관리한계 차트 |

| `feat/analytics-docs` | SQL 분석, README와 학습 설명 |

기능별 변경과 검증은 [Pull requests](https://github.com/lcww070513-blip/semi_guard/pulls?q=is%3Apr)에서 확인할 수 있습니다. PR의 열림·병합 상태는 작업에 따라 바뀌므로 GitHub 기록을 기준으로 확인합니다. 커밋 수나 브랜치 수 자체보다 변경 이유와 검증 근거를 설명하는 것이 중요합니다.

## 설계 선택

**화면과 계산을 분리했습니다.** `detector.py`는 Streamlit을 호출하지 않고 입력 값으로 판정 결과를 반환합니다. 따라서 화면을 띄우지 않고 경계값과 우선순위를 테스트할 수 있습니다. `service.py`는 생성·판정·저장을 연결하고, `views`는 사용자 입력과 표시를 담당합니다. 클래스 대신 역할이 좁은 함수를 사용했습니다.

**표본 표준편차를 사용했습니다.** 생성한 기준 샘플에서 평균과 표준편차를 추정하며 `ddof=1`로 나눗셈의 분모를 표본 수보다 1 작게 합니다. 표본이 1개면 이 값을 구할 수 없고 모두 같은 값이면 표준편차가 0이므로 기준 생성을 거부합니다. 이 선택이 실제 제조 기준이라는 의미는 아닙니다.

**판정과 작업 진행 상태를 구분했습니다.** 정상·주의·이상은 측정값에 대한 판단이고, 미확인·점검 중·조치 완료는 이벤트 처리 상황입니다. 체크리스트 완료만으로 센서가 정상으로 바뀌면 데이터 의미가 왜곡되므로 서로 별도로 관리합니다.

**DB 제약으로 중복을 방지했습니다.** 코드에서 먼저 존재 여부를 조회하는 것만으로는 동시에 저장할 때 중복이 생길 수 있습니다. `UNIQUE` 제약과 충돌 시 저장 생략을 함께 사용합니다. 한 측정값을 다시 처리해도 이벤트를 반복 생성하지 않습니다.

**기록은 추가하고 상태는 갱신합니다.** 점검 내용을 수정할 때 이전 내용을 없애지 않고 새 행을 저장합니다. 이벤트의 현재 상태와 새 기록을 같은 트랜잭션에서 처리하여 한쪽만 저장되는 상황을 방지합니다. 폼이 읽었던 최신 기록 번호가 바뀌면 저장을 거부하고 재확인을 요청합니다. 이는 로그인·사용자별 감사 시스템을 구현했다는 뜻은 아닙니다.

**이벤트 집계는 SQL에 맡겼습니다.** 전체 이벤트를 Python으로 가져와 반복 계산하지 않고 날짜·설비·센서별 `GROUP BY` 결과만 조회합니다. pandas의 형태 변환은 집계와 구별합니다. 날짜에 이벤트가 없으면 0을 채워 선 그래프에서 빈 날짜가 빠지지 않게 합니다.

**Streamlit 재실행을 고려했습니다.** 입력 변경 때 스크립트가 다시 실행됩니다. 초기화는 DB의 기준 버전 존재 여부로 한 번만 수행하고, 데이터 추가는 버튼으로 구분합니다. 폼 제출은 사용자 입력을 모아 한 번에 저장합니다.

## 직접 확인할 실험

1. `generate_data()`에 고정 시각과 같은 시드를 두 번 넣어 결과를 비교합니다. 시각만 바꾸면 어떤 컬럼이 달라지는지 확인합니다.
2. 평균 70, 표준편차 2인 가상 기준으로 74, 74.001, 76, 76.001을 판정합니다. 예상 결과는 정상, 주의, 주의, 이상입니다. 하한에서도 대칭으로 확인합니다.
3. 진동값을 평균보다 크게 낮춰도 정상인 이유를 설명합니다. 이 단순 규칙의 한계도 함께 생각합니다.
4. 한 시각의 온도·압력을 모두 이상으로 만들면 설비 이상 수와 이벤트 수가 각각 어떻게 변하는지 확인합니다.
5. 같은 측정값을 두 번 저장했을 때 측정 행과 이벤트 행 수가 증가하지 않는지 테스트를 읽어 확인합니다.
6. 한 이벤트를 점검 중, 조치 완료 순서로 저장하고 DB에서 기록 두 개와 최신 상태를 확인합니다.
7. 기준 샘플에 큰 값을 섞으면 평균과 표준편차가 어떻게 바뀌는지 별도 임시 데이터로 실험합니다. 원본 데모 DB는 보존합니다.

## 설명 연습 질문

- 규칙 기반 판정인데 머신러닝 없이도 어떤 문제를 해결할 수 있나요?
- 정확히 3σ인 값을 주의에 포함한 이유와 이를 검증하는 방법은 무엇인가요?
- 생성 설정의 평균과 실제 산출 평균이 다른 이유는 무엇인가요?
- 운영 데이터로 기준을 계속 재계산하면 어떤 문제가 생길 수 있나요?
- 같은 이상이 10개 시각에서 발생했을 때 현재 시스템은 몇 건으로 세나요?
- 왜 SQL 집계를 사용했고, 어떤 부분은 pandas가 담당하나요?
- 조치 완료 후에도 현재 설비 상태가 이상일 수 있는 이유는 무엇인가요?
- 실제 현장에 적용하려면 어떤 검증·데이터·권한 관리가 추가로 필요한가요?

답변은 실제 코드와 실행 결과를 근거로 작성하세요. 가상 데이터로 실제 고장 예측 성능이나 생산성 향상을 입증했다고 표현하지 않습니다.
